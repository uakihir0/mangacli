# 2. アーキテクチャ

## 2.1 全体構成

```text
            ┌──────────────┐   ┌──────────────────────┐
 YAML ────▶ │  Loader      │   │ TypeScript オブジェクト │
            └──────┬───────┘   └──────────┬───────────┘
                   ▼                      ▼
            ┌─────────────────────────────────────┐
            │ Normalizer（省略記法の展開）          │
            │ Validator（スキーマ検証）              │
            │ Resolver（カスケード・単位・参照・ID・シード）│
            └──────────────────┬──────────────────┘
                               ▼ ResolvedDocument
            ┌─────────────────────────────────────┐
            │ Resource Manager                     │◀── Font / Asset Resolver
            │（フォント読み込み・素材のメタ情報・字形確認）│
            └──────────────────┬──────────────────┘
                               ▼
            ┌─────────────────────────────────────┐
            │ Layout Engine                        │
            │ ページ幾何 → コマ割り → 組版 → 吹き出し  │
            │ → 自動配置 → しっぽ → 効果の領域        │
            └──────────────────┬──────────────────┘
                               ▼ LayoutTree
            ┌─────────────────────────────────────┐
            │ Generator                            │
            │ 手描き化エンジン（Ink）・効果・トーン   │
            └──────────────────┬──────────────────┘
                               ▼ DisplayList（IR）
       ┌──────────────┬────────┴───────┬──────────────┐
       ▼              ▼                ▼              ▼
  Raster Backend   SVG Backend     PDF Backend    外部（エディタ等）
       │
       ▼
  Post Process（カラーモード変換・網点化・仕上げ・切り抜き・トンボ）
       │
       ▼
  Encoder / Writer（PNG・JPEG・WebP・TIFF … / 命名 / メタデータ）
```

CLI は API の薄いラッパーとする。CLI だけが持つ機能（ファイル監視、プレビューサーバー、終了コード）以外の処理は、すべて API から利用できなければならない。

## 2.2 処理パイプライン

| 段階 | 入力 | 出力 | 主な処理 |
|---|---|---|---|
| 1. Load | ファイルパス / 文字列 | 生のドキュメント + ソースマップ | YAML の解析、インポート・インクルードの読み込み、各値の出現位置（ファイル・行・列）の記録 |
| 2. Normalize | 生のドキュメント | 正規形のドキュメント | 省略記法の展開（[3.9](03-document-format.md#39-省略記法)）、`dialogue` から吹き出しへの展開、文字列形式の値（`tone(30%)` など）の構造化 |
| 3. Validate | 正規形のドキュメント | 診断 | スキーマ検証、参照の存在確認、ID の重複確認 |
| 4. Resolve | 正規形のドキュメント | ResolvedDocument | 既定値・スタイル・キャラクター設定のカスケード、絶対単位の mm への統一、自動 ID の付与、シードの導出 |
| 5. Prepare | ResolvedDocument | リソース表 | フォントの読み込み（カタログのフォントの取得を含む、[7.3.10](07-text.md#7310-フォントのカタログと取得)）とシェーピングの準備、素材の寸法・アルファの有無の取得、字形の欠落の確認 |
| 6. Layout | ResolvedDocument + リソース | LayoutTree | ページ・コマの幾何、読み順、% と `auto` の解決、組版、吹き出しの寸法、自動配置、しっぽ、効果の領域の計算 |
| 7. Generate | LayoutTree | DisplayList | 形状の手描き化、効果線・トーン・漫符の生成、描画順の確定 |
| 8. Render | DisplayList | ラスタ / ベクタ | バックエンドによる描画 |
| 9. Post Process | ラスタ | ラスタ | カラーモード変換、網点化、2 値化、仕上げ、切り抜き、トンボ |
| 10. Encode / Write | ラスタ / ベクタ | ファイル / バイト列 | エンコード、ファイル名の決定、メタデータの埋め込み |

- 段階 1〜5 はドキュメント全体に対して 1 回行う。段階 6〜10 はページごとに独立に行い、並列化できる。
- 各段階の出力は API から取得できなければならない（例: レイアウトだけを計算してエディタに表示する）。
- 段階 3 でエラーがある場合は段階 4 以降に進まない。警告は進行を妨げない（`strict` 指定時を除く）。

## 2.3 モジュール構成

パッケージ内部のディレクトリ構成を次のとおりとする（名称は実装時に調整してよい）。

| モジュール | 責務 |
|---|---|
| `schema/` | Zod スキーマ、入力型・解決済み型、JSON Schema の生成 |
| `loader/` | YAML の解析、ソースマップ、インポート、インクルード、設定ファイル |
| `normalize/` | 省略記法の展開、文字列形式の値の解析 |
| `resolve/` | カスケード、単位、参照、ID、シード |
| `units/` | 長さ・角度・色の解析と変換 |
| `geometry/` | ベクトル、行列、ベジェ、平坦化、ポリゴンのブール演算、オフセット |
| `random/` | 擬似乱数生成器、ハッシュ、ノイズ関数 |
| `ink/` | 手描き化エンジン（ストロークモデル、ペン、形状の分解） |
| `layout/page/` | ページの幾何、コマ割り、読み順 |
| `layout/text/` | シェーピング、改行、禁則、ルビ、縦中横 |
| `layout/balloon/` | 吹き出しの形状、寸法、しっぽ、連結、自動配置 |
| `elements/` | 各要素（image、text、sfx、effect、fill、mark、draw、group、scatter）の生成 |
| `effects/` | 効果線・トーン・漫符の生成器 |
| `ir/` | 表示リストの型と構築・検証・シリアライズ |
| `backends/raster/` | ラスタバックエンド |
| `backends/svg/` | SVG バックエンド |
| `backends/pdf/` | PDF バックエンド |
| `postprocess/` | カラーモード変換、網点化、仕上げ、切り抜き、トンボ |
| `output/` | エンコード、命名、メタデータ、付随出力 |
| `plugins/` | プラグインの登録、組み込みプラグイン |
| `diagnostics/` | 診断の型、メッセージカタログ（日本語・英語）、整形 |
| `cli/` | コマンド、監視、プレビューサーバー |

依存の方向は `cli → api → (各モジュール)` とし、`geometry`、`random`、`units`、`ir` は他のモジュールに依存してはならない。Node.js 固有の API（`fs`、`worker_threads` など）は `loader`、`output`、`cli`、プラットフォームアダプタに閉じ込め、それ以外のモジュールは環境非依存に保つ（将来のブラウザ対応のため）。

## 2.4 データモデルの段階

| モデル | 説明 | 単位 | 公開 |
|---|---|---|---|
| `MangaDocumentInput` | 利用者が書く入力。省略記法を含む | 単位付き文字列・数値 | 型を公開 |
| `MangaDocument` | 正規形。省略記法を展開済み | 単位付き文字列・数値 | 型を公開 |
| `ResolvedDocument` | カスケード済み。すべての長さは mm の数値、色は RGBA、参照は ID に解決済み | mm | 型を公開 |
| `LayoutTree` | ページごとの幾何。コマの多角形、要素の変換行列と外接矩形、組版結果、吹き出しの輪郭 | mm | 型を公開 |
| `DisplayList` | 描画命令の木 | mm | 型を公開 |

### 2.4.1 ResolvedDocument の要件

- すべての要素が一意な ID を持つ（自動付与を含む）。
- すべての要素が、導出済みのシード（32 ビット符号なし整数）を持つ。
- 絶対単位の長さはすべて mm の数値である。`%`、`em`、`auto`、参照、自動配置の位置は、基準となる領域や組版の結果がレイアウトで決まるため、未解決の形（値と基準の組）のまま残す。
- 自動 ID とシードは、レイアウトの結果（読み順など）に依存せずに決まる（[3.7.1](03-document-format.md#371-id)）。
- すべての色が sRGB の RGBA（各 0〜1）である。
- 各値がどのファイル・行・列に由来するか（カスケードのどの段階に由来するかを含む）を追跡できる。診断と `inspect` コマンドで使う。

### 2.4.2 LayoutTree の要件

ページごとに次を含む。

- ページの各領域（塗り足し、仕上がり、基本枠、安全領域）の矩形
- コマごとの多角形（断ち切り適用後）、表示領域、読み順
- 要素ごとの変換行列、外接矩形、クリップ領域
- テキストごとの組版結果（字形 ID、位置、回転、ルビ・傍点の位置、行の範囲）
- 吹き出しごとの本体輪郭、しっぽの幾何、テキスト領域、連結後の輪郭
- 自動配置の結果と、その評価値（デバッグ用）

LayoutTree は JSON にシリアライズできなければならない（[10.12](10-color-and-output.md#1012-付随出力)）。

## 2.5 表示リスト（IR）

表示リストは、バックエンドに依存しない描画命令の木である。座標はページの塗り足しを含む領域の左上を原点とする mm で表す。

```ts
interface DisplayList {
  version: 1;
  page: { id: string; index: number };
  size: { width: number; height: number };        // 塗り足しを含む mm
  boxes: { bleed: Rect; trim: Rect; baseFrame: Rect; safe: Rect };
  background: Paint | null;                       // null は透過
  root: GroupNode;
}

type Node = GroupNode | PathNode | ImageNode | GlyphRunNode;

interface GroupNode {
  kind: "group";
  transform?: Matrix;            // 2x3 アフィン行列
  opacity?: number;              // 0〜1
  blend?: BlendMode;
  clip?: PathData;               // クリップパス（nonzero）
  mask?: MaskSpec;               // ソフトマスク（輝度またはアルファ）
  children: Node[];
  tag?: NodeTag;
}

interface PathNode {
  kind: "path";
  path: PathData;                // M / L / C / Q / Z（mm）
  fillRule: "nonzero" | "evenodd";
  paint: Paint;
  tag?: NodeTag;
}

interface ImageNode {
  kind: "image";
  asset: AssetHandle;            // 素材への参照（デコードはバックエンド側）
  transform: Matrix;             // 素材の 1px を mm 空間へ写す行列
  sourceRect?: Rect;             // 素材上の切り抜き（px）
  filters: ResolvedFilter[];
  smoothing: "high" | "medium" | "none";
  tag?: NodeTag;
}

interface GlyphRunNode {          // 文字の付加情報（描画しない。任意）
  kind: "glyphs";
  text: string;                  // 元の文字列
  runs: { glyphId: number; font: string; x: number; y: number; rotate: number }[];
  tag?: NodeTag;
}

type Paint =
  | { type: "solid"; color: RGBA }
  | { type: "tone"; tone: ToneSpec; color: RGBA }   // 網点・万線・砂目など
  | { type: "linear-gradient" | "radial-gradient"; stops: Stop[]; geometry: GradientGeometry }
  | { type: "pattern"; asset: AssetHandle; transform: Matrix };

interface NodeTag {
  elementId: string;
  elementType: string;           // image / balloon / text / ...
  role: "art" | "fill" | "tone" | "ink" | "text" | "frame" | "furniture" | "debug";
  separation: string;            // 分版名（10.10）
}
```

- 線（ストローク）の命令は持たない。手描き化エンジンが、すべての線を太さの変化を含む塗りの輪郭に変換する。これにより、各バックエンドで線の見た目が一致する。デバッグオーバーレイ用の極細線だけは、輪郭化した細い塗りで表す。
- 文字は字形のアウトラインを `PathNode`（`tag.role: "text"`）として描く。フォントのラスタライザの違いによる差をなくし、手書き風の変形を可能にするためである。`GlyphRunNode` は、PDF の検索用テキストやエディタでの選択のための付加情報であり、バックエンドは描画に使わない。
- トーンは `tone` 塗りとして保持し、網点の生成はバックエンドが出力解像度に合わせて行う（[10.3](10-color-and-output.md#103-トーンの描画)）。
- 表示リストは JSON にシリアライズでき、数値を 0.001 mm に丸めた正規形でスナップショットテストに使えなければならない。
- `tag` により、要素の ID と表示リストのノードを対応付ける。エディタでの当たり判定、分版出力、デバッグに使う。

## 2.6 バックエンド

| バックエンド | 出力 | 優先度 | 方式 |
|---|---|---|---|
| raster | RGBA / グレー / 2 値のビットマップ | P0 | Skia 系の 2D 描画ライブラリで表示リストを描画する |
| svg | SVG 文書 | P1 | 表示リストを SVG 要素に変換する。トーンは可能な限り `<pattern>` で表す |
| pdf | PDF | P1 | ベクタとして書き出す。設定によりページをラスタ化して埋め込む |
| canvas | ブラウザの Canvas 2D / OffscreenCanvas | P2 | ブラウザ対応用 |

バックエンドは次のインターフェースを実装する。

```ts
interface Backend<TOut> {
  name: string;
  capabilities: {
    vector: boolean;            // ベクタ出力か
    colorModes: ColorMode[];    // 対応するカラーモード
    blendModes: BlendMode[];    // 対応する合成モード
    softMask: boolean;
  };
  render(list: DisplayList, options: BackendRenderOptions): Promise<TOut>;
}
```

バックエンドが対応しない機能（合成モードなど）を表示リストが含む場合は、近似して描画し、警告 `RENDER_FEATURE_APPROXIMATED` を出す。

## 2.7 フォントとテキストシェーピング

- テキストのシェーピング（字形の選択と配置）は HarfBuzz（WebAssembly 版）で行う。縦書きでは方向を上から下（TTB）にする。HarfBuzz は TTB で OpenType の `vert` 機能を自動で適用し、縦組み用字形と縦書きの送り・字形の位置（フォントの縦書きのメトリクスによる）を返す。`vrt2` は欧文の扱い（[7.4.4](07-text.md#744-欧文と数字)）と衝突するため使わない。
- 字形のアウトラインはフォントから直接取得し、表示リストのパスにする。OS のフォントラスタライザは使わない。
- フォントは、ドキュメント・設定で登録したファイル、または同梱のカタログのフォント（版とハッシュを固定し、必要なときに取得する）を使う。OS にインストールされたフォントの暗黙の利用は行わない（再現性のため）。OS のフォントを使う場合は明示的に指定する（P1、[7.3](07-text.md#73-フォント)）。
- フォントの解析結果、シェーピング結果（テキスト・フォント・サイズ・機能の組をキーとする）はキャッシュする。

## 2.8 画像処理

- 素材のデコード、リサイズ、色空間の変換（埋め込み ICC プロファイルから sRGB への変換）、エンコードには libvips 系のライブラリを使う。
- 素材は、出力解像度で必要な画素数を上限としてデコード・縮小してからバックエンドに渡し、メモリ使用量を抑える。縮小には Lanczos 系のフィルタを使う。
- フィルタ（[5.6](05-elements-and-images.md#56-フィルタ)）は、出力解像度に縮小した後の画素に適用する。網点化フィルタは、出力の画素格子に揃えて適用する。
- デコード済みの素材は、素材の内容ハッシュと縮小後の寸法をキーとしてキャッシュする。

## 2.9 決定性と再現性

1. 乱数はすべて `random/` の擬似乱数生成器から得る。`Math.random()`、時刻、プロセス ID、ハッシュマップの列挙順に依存してはならない。
2. 各要素のシードは、ドキュメントのシードと要素の ID から導出する（[9.2](09-hand-drawn.md#92-乱数とノイズ)）。ある要素を変更しても、ID の変わらない他の要素の線は変わらない。自動 ID は要素の追加・削除で変わりうるため（[3.7.1](03-document-format.md#371-id)）、線を固定したい要素とページには明示的な ID を付ける。
3. 浮動小数点の計算は、同じ JavaScript エンジンであれば同じ結果になる演算のみで構成する。`Math.sin`、`Math.pow` などの超越関数は、JavaScript エンジン（V8）のバージョンやプラットフォームで結果が変わりうるため、表示リストの比較は 0.001 mm に丸めて行う。丸めの境界付近の値は丸めても一致しない場合があるため、比較では ±0.001 mm の差を許容する。
4. 文節の区切り（`Intl.Segmenter`）は Node.js に同梱される ICU のバージョンに依存する（[7.6.2](07-text.md#762-文節に近い単位phrase)）。
5. 再現性の保証水準は次のとおりとする。

| 水準 | 条件 | 保証 |
|---|---|---|
| L1 | 同じ入力・同じライブラリのバージョン・同じ Node.js のメジャーバージョン | 表示リスト（丸めた正規形）が ±0.001 mm の範囲で一致する |
| L2 | L1 + 同じプラットフォーム・同じネイティブ依存のバージョン | ラスタ出力のバイト列が一致する |
| L3 | L1 + 異なるプラットフォーム | ラスタ出力の画素の差が許容範囲内（[14.3](14-quality.md#143-ビジュアルリグレッションテスト)） |

6. 出力ファイルのメタデータには、既定で作成日時を含めない。環境変数 `SOURCE_DATE_EPOCH` が設定されている場合はその時刻を使う。
7. 見た目やレイアウトを変えるアルゴリズム・既定値の変更は、エンジンのバージョン（トップレベルの `engine`、[3.19.1](03-document-format.md#3191-エンジンのバージョンengine)）を上げて行う。`engine` を明示したドキュメントは、ライブラリを更新しても同じ結果になる。

## 2.10 並列化・キャッシュ・性能

### 並列化

- 段階 1〜6（Load〜Layout）はメインスレッドで行う。利用者が関数として渡すもの（リゾルバー、`fs`、`segmenter`、`logger`、`onProgress`）はメインスレッドでだけ呼び出す。
- 段階 7〜10（Generate〜Encode）は、ページ単位でワーカースレッドに分散する。既定の並列数は `min(論理 CPU 数, 4)` とし、出力解像度が高い場合（1 ページあたり 2,000 万画素超）は、メモリ使用量を見積もって並列数を下げる。
- フォントのデータ、素材の画素、LayoutTree は、ワーカーへ共有メモリまたは転送可能なバッファで渡す。
- ワーカーは、プラグインをモジュール指定子（[11.8.1](11-api.md#1181-定義)）から読み込む。モジュール指定子を持たないプラグイン（その場で作ったオブジェクトなど）を使う場合は、段階 7〜10 もメインスレッドで行い、情報（`RENDER_SINGLE_THREAD`）を出す。
- 並列数を変えても出力は一致しなければならない。

### キャッシュ

| キャッシュ | キー | 寿命 |
|---|---|---|
| フォント | ファイルの内容ハッシュ | レンダラーの寿命（ディスクキャッシュ任意） |
| カタログのフォントのファイル | カタログ ID・太さ・項目の版・SHA-256 | ユーザーのキャッシュ（`fontCacheDir`）に永続。プロジェクト間で共有する |
| シェーピング | テキスト・フォント・サイズ・機能・方向 | レンダラーの寿命 |
| 素材 | 内容ハッシュ + 縮小後の寸法 + フィルタ | レンダラーの寿命 / ディスクキャッシュ（P1） |
| ページ出力 | ページの ResolvedDocument 部分のハッシュ + 依存リソースのハッシュ + 出力設定 + ライブラリのバージョン | ディスクキャッシュ（P1） |

ページ出力のキャッシュにより、watch で変更のないページの再レンダリングを省略する（P1）。キャッシュの置き場所は既定で `node_modules/.cache/mangacli`、設定で変更できる。

## 2.11 実行環境と配布

| 項目 | 仕様 |

## 2.12 技術選定

下表は推奨する構成である。技術検証（[15.1](15-roadmap.md#151-マイルストーン) の M0）で問題が見つかった場合は、代替候補に切り替えてよい。

| 領域 | 推奨 | 理由 | 代替候補 |
|---|---|---|---|
| 言語 | TypeScript（strict） | 型による API の安全性 | - |
| YAML | `yaml` | YAML 1.2 準拠、ソース位置の取得、1.2 の Core Schema のままマージキーを有効にできる（[3.2](03-document-format.md#32-yaml-の扱い)） | `js-yaml` |
| スキーマ | `zod`（v4） | 型推論、JSON Schema の生成、詳細なエラー | `valibot` |
| シェーピング | `harfbuzzjs`（WebAssembly） | 縦書き（TTB）、OpenType 機能、字形アウトラインの取得 | `fontkit` |
| フォント解析 | `fontkit` | WOFF / WOFF2 の展開、メタ情報、コレクション | `opentype.js` |
| ラスタ描画 | `@napi-rs/canvas`（Skia） | プリビルド、システム依存なし、高速、Path2D | `skia-canvas` |
| 画像入出力 | `sharp`（libvips） | デコード、縮小、ICC、1 bit PNG / TIFF の出力 | `@napi-rs/canvas` の内蔵機能 |
| ポリゴン演算 | Clipper2 系（WebAssembly または JS 移植） | 和・差・オフセットが堅牢 | `polygon-clipping` |
| PDF | `pdf-lib` | Pure JS、ページボックスの設定。1 ビット画像（CCITT G4 など）の埋め込みは対応しないため、画像の XObject は自前で書き出す | `pdfkit` |
| CLI 引数 | `cac` | 軽量、サブコマンド | `commander` |
| ファイル監視 | `chokidar` | プラットフォーム差の吸収 | `node:fs` の watch |
| フォントの取得 | Node.js 組み込みの `fetch` と `node:crypto`（SHA-256） | 依存を増やさない | - |
| プロセス間の排他 | ロックファイル（自前実装、または `proper-lockfile`） | 同時取得の防止 | - |
| テスト | `vitest`、`pixelmatch`、`fast-check` | 単体・画像比較・性質テスト | - |
| 乱数・ノイズ | 自前実装 | 決定性をライブラリの更新に左右されないため | - |

## 2.13 セキュリティ

1. YAML のカスタムタグ（`!!js/function` など）は解釈しない。未知のタグはエラーとする。
2. エイリアスの展開数に上限を設け（既定 10,000 ノード）、いわゆる Billion Laughs 攻撃を防ぐ。
3. ファイル参照（素材、フォント、インポート）は、プロジェクトルート（既定はエントリの YAML があるディレクトリ）の内側に限る。外側を参照する場合は `allowOutsideRoot` を明示する。シンボリックリンクは解決後のパスで判定する。
4. URL による素材の取得は既定で無効とする。有効にした場合も、許可するホストのリスト、タイムアウト、最大サイズを適用する。リダイレクト先も同じ規則で検査し、プライベート・ループバック・リンクローカルのアドレス（名前解決の結果で判定する）への接続は、明示的に許可しない限り拒否する。
5. ドキュメントにはコードを書けない。プラグインは設定ファイルまたは API でのみ読み込む（信頼できるコードとして扱う）。
   - カタログのフォントの取得（[7.3.10](07-text.md#7310-フォントのカタログと取得)）は、素材の URL の取得とは別の許可（`fontDownload`、既定 `auto`）とする。取得先はカタログの URL（または `fontMirror`）に限り、HTTPS とハッシュの検証を必須とする。ドキュメントは任意の URL のフォントを指定できない。

6. SVG の素材は、外部の資源の参照（`<image href>`、外部 CSS、フォント）と XML の実体参照を無効にしてラスタ化する。
7. JavaScript・TypeScript の設定ファイルはコードとして実行される。CLI は設定ファイルを自動で探すが、信頼できないリポジトリを CI でレンダリングする場合は `--no-config` を使う。API は既定で設定ファイルを探さない（[11.5](11-api.md#115-レンダリングオプション)）。
8. 入力と処理量の上限を設ける。上限は設定・API の `limits` で変更できる。

| キー | 上限 | 既定値 |
|---|---|---|
| `maxSourceBytes` | YAML ファイルのサイズ | 10 MB |
| `maxAliasNodes` | エイリアスの展開後のノード数 | 10,000 |
| `maxPages` | ページ数 | 1,000 |
| `maxElementsPerPage` | 1 ページあたりの要素数 | 5,000 |
| `maxTextLength` | 1 つの要素の本文の文字数 | 2,000 |
| `maxOutputPixels` | グレー・カラー・RGBA 互換経路の出力 1 ページの画素数（分割見開きは片側ごと） | 2 億 |
| `maxOutputBytes` | 不透明 1-bit PNG/TIFF/PDF の推定作業メモリ（ページごと） | 384 MiB。印刷プロファイルは通常ページ・見開きともにノード作業領域込みで 4 GiB |
| `maxAssetPixels` | 素材 1 枚のデコード後の画素数 | 3 億 |
| `maxAssetBytes` | 素材 1 つのファイルサイズ | 200 MB |
| `maxEffectLines` | 効果 1 つあたりの線の本数（`passes` の合計） | 20,000 |
| `maxScatterItems` | 散布 1 つあたりの個数 | 5,000 |
| `maxDpi` | 出力解像度 | 2,400 |
| `minHandResolution` | `hand.resolution` の下限 | 0.05 mm |
| `maxLpi` | トーンの線数 | 200 |
| `pageTimeoutMs` | 1 ページの処理時間 | 120,000 ms |

分割見開きは片側ずつラスタライズ・エンコードする。不透明 1-bit PNG/TIFF（既定 CCITT G4）/PDF は最大 400 万画素の水平バンドを 1bpc ページバッファへ直接格納し、ページ全体の RGBA は保持しない。トンボもバンド単位で描画する。論理ページ座標を保つため、画像・フィルター・ディザのノード内処理範囲は変えない。

1-bit 出力は画素数ではなく `maxOutputBytes` で事前検査する。推定値は行パディング込み packed ページ容量の 4 倍（ページ・エンコーダ用）、最大バンド画素数の 24 倍、32 MiB の固定余裕、およびレイアウトから求めたノード作業領域のピークを含む。ノード作業領域を除く出力寸法の検査には、プロファイルやページ種別を問わず既定の 384 MiB を使う。上限を明示すると、両方の検査にその値を使う。これは RSS の厳密な上限ではなく、ネイティブライブラリや GC の追加コストは環境に依存する。既定値で B4 / 1200 dpi 分割（トンボ付きも可）は通るが、A3 / 2400 dpi 結合などの巨大出力は拒否する。仕上げ処理（`finish`）、`afterRender` フック、デバッグ表示は RGBA 互換経路と画素数上限を使う。透明出力・色分解も 1bpc ではないため同じ互換経路を使う。

9. 出力先は指定されたディレクトリの内側に限る。ファイル名のテンプレートに由来するパス区切り文字や `..` は無害化する。ドキュメントに書かれた `output.dir` もプロジェクトルートの内側に限る。API の `ignoreDocumentOutput: true` を指定すると、ドキュメントの `output`（出力先・名前・解像度など）を無視する（信頼できないドキュメントを扱うサーバー向け）。
10. プレビューサーバーは既定で `127.0.0.1` にのみバインドする。


## 2.14 ロギングと診断

- 処理中の出来事は、診断（[13-validation.md](13-validation.md)）とログに分ける。診断は利用者の入力に関する報告、ログは処理の進行に関する報告である。
- ログのレベルは `silent`、`error`、`warn`、`info`、`debug`、`trace` とする。既定は `info`。
- API では、ログの出力先を利用者が差し替えられる（`logger` オプション）。既定では何も出力しない。
- 各段階の所要時間を `debug` レベルで記録し、`--timings` で一覧表示できる（P1）。
